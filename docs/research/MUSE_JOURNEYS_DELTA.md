## 1. Independent findings (recorded before reading Grok)

These are the load-bearing code facts my pre-Grok pass established. Each is stated as intent → code path → observed outcome boundary.

1. **All conversational state is volatile.** [AppModel.swift](../../app/PocketGlimmer/AppModel.swift:52) holds `chat: [ChatItem]` in memory; `ChatItem` is not `Codable`; the pending `PlannedAction` lives only in `chat[i].pending` ([AppModel.swift](../../app/PocketGlimmer/AppModel.swift:218)). SQLite (`pocket.sqlite`, Application Support) persists facts and telemetry only. `PocketGlimmerApp.swift` has no `scenePhase` handling and no state restoration. Process death therefore loses the conversation, any unconfirmed card, and any clarify context.
2. **A single `busy` flag rejects, and in three places destroys, work.** `send` returns a canned sentence when busy ([AppModel.swift](../../app/PocketGlimmer/AppModel.swift:199)); the busy guard runs **before** `SharedInbox.put` (line 199 vs line 202). A finished voice recording is discarded when busy ([VoiceCapture.swift](../../app/PocketGlimmer/Capture/VoiceCapture.swift:114)).
3. **Permissions are requested once, swallowed, and never re-checked.** `SystemActions.requestAccess` uses `try?` for Reminders, Events and Contacts ([SystemActions.swift](../../app/PocketGlimmer/Actions/SystemActions.swift:15)) and is called only from onboarding ([OnboardingView.swift](../../app/PocketGlimmer/Views/OnboardingView.swift:29)). No view links to Settings (`openSettings` appears nowhere). Action code never reads `EKAuthorizationStatus` or `CNAuthorizationStatus` before searching or saving; the only status read in the app is for the privacy scrubber's name list ([AppModel.swift](../../app/PocketGlimmer/AppModel.swift:160)).
4. **Disambiguation does not bind an identity.** `searchContacts` returns display strings, capped at 7 ([SystemActions.swift](../../app/PocketGlimmer/Actions/SystemActions.swift:21)); the chosen label's hint is stripped by `displayName` ([SystemActions.swift](../../app/PocketGlimmer/Actions/SystemActions.swift:112)); `addresses(for:)` then takes the **first** unified contact matching the bare name and the caller takes its **first** phone number ([SystemActions.swift](../../app/PocketGlimmer/Actions/SystemActions.swift:114), [:79](../../app/PocketGlimmer/Actions/SystemActions.swift:79)). The same pattern exists in the skill runner's `phoneNumber(for:)` ([SkillRunner.swift](../../app/PocketGlimmer/Actions/SkillRunner.swift:71)).
5. **Times are phrases until `NSDataDetector`, and the resolved instant is never shown on the no-card path.** `SystemActions.date(from:)` takes the detector's first match with no timezone handling ([SystemActions.swift](../../app/PocketGlimmer/Actions/SystemActions.swift:128)); events default to now + 1 hour with a fixed 1-hour duration ([SystemActions.swift](../../app/PocketGlimmer/Actions/SystemActions.swift:64)); reminders use `Calendar.current` components ([:56](../../app/PocketGlimmer/Actions/SystemActions.swift:56)). The tool-path confirmation prompt is unlabeled sorted values ([Assistant.swift](../../core/Sources/PocketCore/Assistant.swift:231)). The `timing` and `notificationTriage` decision sets exist ([Decision.swift](../../core/Sources/PocketCore/Decision.swift:105)) but are never consulted on the action path.
6. **Nothing created can be edited, moved, cancelled or undone from the app.** The six tools are create/find/send/lookup/recall only ([Decision.swift](../../core/Sources/PocketCore/Decision.swift:60)); `perform` returns sentences and discards EventKit identifiers ([SystemActions.swift](../../app/PocketGlimmer/Actions/SystemActions.swift:49)). Memory deletion is one swipe per fact ([MemoryView.swift](../../app/PocketGlimmer/Views/MemoryView.swift:59)).
7. **Notifications are a dead end.** `Nudge.factIDs` are computed ([Proactive.swift](../../core/Sources/PocketCore/Proactive.swift:30)) and then discarded by `AppModel.handleTrigger`, which posts content with a random identifier, no `categoryIdentifier`, no `userInfo`, and the app registers no notification delegate or categories ([AppModel.swift](../../app/PocketGlimmer/AppModel.swift:243)).
8. **Voice is cloud-only, hold-only, and English-biased.** The mic is a press-and-hold `DragGesture`, requires `isOnline` and a Meta key, and drops the recording if busy ([VoiceCapture.swift](../../app/PocketGlimmer/Capture/VoiceCapture.swift:82)); transcription defaults to English ([MetaMultimodal.swift](../../core/Sources/PocketCore/MetaMultimodal.swift:691)). [project.yml](../../app/project.yml:40) has no `NSSpeechRecognitionUsageDescription`, so no on-device speech path exists even as an option. Accessibility labelling is sparse (8 `accessibilityLabel` hits app-wide, verified by search).

## 3. NEW findings in detail

### N1. A correct pick is discarded before the send (wrong-recipient risk)

**Flow (caregiver/worker).** "Text Sam I'm running late" → two Sams → the model or the user picks "Sam Ortiz (brother)" → confirm → Messages opens.

**Code.** `Assistant.toolPath` stores the picked **label** into `args["contact"]` ([Assistant.swift](../../core/Sources/PocketCore/Assistant.swift:208)); the skill path does the same ([ActionPlanner.swift](../../core/Sources/PocketCore/ActionPlanner.swift:125)). At perform time, `SystemActions.displayName` strips `" (brother)"`, `addresses(for:)` re-searches by bare name and takes `.first`, and `send_message` takes `phones.prefix(1)` ([SystemActions.swift](../../app/PocketGlimmer/Actions/SystemActions.swift:76)). Contacts framework ordering for same-name unified contacts is not a user-visible guarantee, so `.first` is an arbitrary Sam; and for the right Sam, the first number may be a landline or an old number. The user did everything right and can still message the wrong person — the worst failure class for a messaging assistant, worse than a clarification loop.

**What Grok said.** Journeys J2 covers the "Which Sam?" question and stale labels, and advises re-resolving at confirm time. It does not identify that the *successful* pick is itself thrown away, nor the first-number choice. The shared contract does fix the identity half: `ContactBinding` carries a `CNContact` identifier, "the session never selects `matches[0]`", and confirm re-resolves by identifier ([EFFECT_RECOVERY_CONTRACT.md](../../docs/research/EFFECT_RECOVERY_CONTRACT.md:216)). That is exactly why this is a strengthening note, not a plan change — but the contract still says "Phone and email are resolved at perform time from Contacts" without saying **which** number when several exist.

**Smallest change.** (a) In Slice 1's `ContactCandidate`, keep the identifier (contract already does) and add the chosen method: when the bound contact has more than one phone/email, the draft card gains a method choice (labelled "mobile", "home", number suffix) instead of `prefix(1)`. (b) Until Slice 1 lands, a two-line stopgap is *not* recommended — half-binding by name would create a second identity path the contract explicitly rejects.

**Acceptance.** New device gate **A21**: two contacts with the identical name "Sam Ortiz", the picked one second in Contacts order, each with two numbers; confirm must open Messages addressed to the picked contact's chosen number. Core gate: a fake `PhoneEffects` whose `resolveContacts` returns two same-name candidates must show `canConfirm == false` until an identifier **and** method are chosen; no test may assert on display-name matching.

**Plan impact.** Slice 1 acceptance amendment only. Priority **P1** because the failure is a wrong-person send.

### N2. "Mom" is a memory alias, not a contact query

**Flow (caregiver/student).** The user once said "My mom's name is Dana Lee". Weeks later: "Text Mom I'll be home by 8."

**Code.** The relation rule stores subject `Dana Lee` with aliases `["mom", "my mom"]` ([Memory.swift](../../core/Sources/PocketCore/Memory.swift:336)), and alias-aware retrieval exists for *recall* ([Memory.swift](../../core/Sources/PocketCore/Memory.swift:280)). But the message path searches Contacts for the literal string "Mom" ([Assistant.swift](../../core/Sources/PocketCore/Assistant.swift:202)); nothing maps role words through `MemoryStore.aliases(forSubject:)` or the entity index before `searchContacts`. On most phones there is no contact literally named "Mom", so the journey fails at the exact phrasing families actually use. Grok notes lowercase "mom" misses a capital-letter regex (journeys gap 8) — true, but even a perfectly capitalised "Mom" has no resolution path; the regex is not the root cause.

**Smallest change.** In the draft/lookup path only (never to auto-send): when a contact query matches no contact but exactly one memory entity lists the query among its aliases, offer that entity's name as the card's pre-filled contact choice, resolved to a `ContactBinding` by the normal search. Zero or several alias matches → ordinary clarify. The card, not the model, makes the binding visible.

**Acceptance.** Core: alias hit produces a staged card with the resolved candidate and `perform` count 0; alias matching two entities produces a choice, never a pick. Device **A22**: with "Dana Lee" stored as mom and present in Contacts, "Text Mom …" reaches a confirm card naming Dana Lee; with Dana Lee absent from the limited Contacts set, the copy says she is outside the set the app can see (composes with Grok A4).

**Plan impact.** Future, but designed to ride Slice 1's `DraftCard` choices rather than a new resolver. Priority **P2**. Trade-off: alias data is memory content; using it for bindings must stay on-device and must never widen what is sent to the cloud scrubber context without the privacy repair's say-so.

### N3. Timezone, DST, travel, and which calendar — the parsed-time failures

**Flows.** (a) *Traveler in Tokyo, phone still showing home time semantics:* "Remind me at 9am tomorrow to call the hotel" — 9am in which zone? (b) *Student:* "Remind me at 2:30am on the spring-forward night to submit" — that local time does not exist. (c) *Worker:* "Add the dentist Friday 1pm" lands on the default calendar, which for many users is a shared family calendar, not work. (d) Any no-card save: the user is never shown the resolved absolute instant, so none of the above is catchable by eye.

**Code.** Argument extraction keeps raw phrases ([Assistant.swift](../../core/Sources/PocketCore/Assistant.swift:243)); `NSDataDetector` resolves them in the current locale/timezone with no handling of an explicit zone phrase ("9am Berlin time" — the zone words are simply not in any argument) ([SystemActions.swift](../../app/PocketGlimmer/Actions/SystemActions.swift:128)); reminder due components are taken from `Calendar.current` ([:56](../../app/PocketGlimmer/Actions/SystemActions.swift:56)); events always use `defaultCalendarForNewEvents`, a fixed one-hour duration, no end, location, attendees or recurrence ([:61](../../app/PocketGlimmer/Actions/SystemActions.swift:61)). The confirmation prompt, when one appears at all, shows unlabeled sorted argument values, not a resolved date ([Assistant.swift](../../core/Sources/PocketCore/Assistant.swift:231)).

**What Grok covered vs missed.** Grok and the contract cover the *unparsed* cases well: no guessed `now+1h`, unparsed time stages a card, `InstantParse` is typed. Neither document examines the *parsed-but-wrong* cases: explicit timezone phrases, DST gaps/overlaps, travel (the phrase was parsed under one zone and fires under another — EventKit reminder due-date components are wall-clock components, so a phone that changes zone reinterprets them), or calendar selection. These are not exotic: they are the standard failure set for reminder apps, and this app's only defence today is a confirmation card that does not show the instant.

**Smallest change.** No new parser. (1) The post-save summary and any draft card must render the resolved instant as date + time + timezone abbreviation (the contract's `userSummary` already names the instant for EventKit receipts — extend the required sentence to include the zone). (2) A phrase containing an explicit zone or city-time hint that the binding cannot honour must become `InstantParse.unparsed`, i.e. a card, not a silent local-time guess. (3) Device-day probes (below) decide whether DST-gap phrases need the same treatment; do not speculate in code before measuring `NSDataDetector` on the phone.

**Acceptance.** Device **A23**: with the phone in one timezone, "Remind me tomorrow 9am" → the saved reminder's due components and the app's summary agree, and both name the zone; repeat after changing the device timezone and record (not assume) whether the firing time moved. **A24**: a DST-transition phrase on the device locale; the card/summary must show the instant the system actually stored, whatever the detector chose. Core: an explicit-zone phrase yields a staged card with `canConfirm` gated on a user-picked instant.

**Plan impact.** Adds acceptance gates to Slice 1; no slice reordering. Priority **P1** for the summary/instant display (cheap, catches whole classes), **P2** for zone-phrase handling.

### N4. Editing what already exists: move, reschedule, cancel

**Flow (every persona).** "Move my dentist to Friday." "Cancel my yoga class." "Change the 5pm reminder to 6."

**Code.** There is no such journey. `find_event` returns the first matching label string and stops ([SystemActions.swift](../../app/PocketGlimmer/Actions/SystemActions.swift:69)); no tool deletes or edits an `EKEvent`/`EKReminder`, and no identifier is ever retained that would allow it. Tellingly, the frozen few-shot set already trains `eventPick` on the context "Cancel my yoga class" ([Decision.swift](../../core/Sources/PocketCore/Decision.swift:199)) — the decision vocabulary anticipates a cancellation the executor cannot perform. The contract's Slice 6 compensation deletes only items **this app created**, verified by attempt token; a pre-existing dentist appointment is explicitly out of its reach.

**Smallest change (future).** A `calendar_edit` capability in the compiled catalog: `find` (existing search) → `eventPick` or card choice → a card showing title, current instant, and the proposed change → EventKit save/remove by `calendarItemIdentifier`, with `objectChanged` protection borrowed from Slice 6 (re-read before writing; if the item changed in Calendar meanwhile, stop). Delete always confirms (compiled floor), regardless of what `confirmBeforeAct` says.

**Acceptance.** Core: edit/delete of an item whose title/instant changed after the card was built returns `objectChanged` and writes nothing. Device **A25**: rename/move an event in Calendar between card and confirm; the app must refuse, not overwrite.

**Plan impact.** Future work after Slice 6 (it reuses Slice 6's read-back discipline against items without attempt tokens). Priority **P2**. It must not be folded into Slice 1: pre-existing items have no attempt identity, and conflating the two would weaken the contract's replay rules.

### N5. Offline voice exists on current iOS and is unplanned

**Flows.** (a) *Traveler/student in airplane mode or a subway:* voice is the fastest input and the only practical one while walking; today the mic refuses before recording ([VoiceCapture.swift](../../app/PocketGlimmer/Capture/VoiceCapture.swift:104)). (b) *Motor-impaired user:* hold-to-talk is already the accessibility gap Grok found; offline it is a total gap. (c) *Privacy-conscious user:* `voice_stays_on_device` currently means "no voice at all" ([SettingsView.swift](../../app/PocketGlimmer/Views/SettingsView.swift:31)).

**Platform facts (retrieved 2026-11-04; see §7 for confidence).** Apple's Speech framework offers on-device transcription via `SpeechAnalyzer`/`SpeechTranscriber`, documented at https://developer.apple.com/documentation/speech/speechanalyzer and widely described as iOS 26+; the older `SFSpeechRecognizer` supports on-device recognition on earlier systems where `supportsOnDeviceRecognition` is true. Either path needs `NSSpeechRecognitionUsageDescription` and Speech authorization — absent from [project.yml](../../app/project.yml:40) today. The deployment target is iOS 18.0, so this must be availability-gated, with a typed fallback, not a target raise.

**What Grok said.** J15 names "No on-device speech recognizer" as missing and the delivery plan has a "Voice review and accessibility" unit (edit transcript, tap-to-record). Neither proposes the on-device recognizer, its authorization journey (denied Speech → typing, with an explanation), its language behaviour (system locale vs the current hard-coded English bias, [MetaMultimodal.swift](../../core/Sources/PocketCore/MetaMultimodal.swift:694)), or the airplane-mode acceptance case. This is the largest *capability* (not just recovery) gap in the journeys space.

**Smallest change (future unit).** A `SpeechTranscribing` seam beside `MultimodalGate.transcribe`: prefer on-device when available and authorized; the transcript then enters the **same transcript-review step** the plan already specifies, and only an edited, submitted transcript reaches `Assistant.handle`. Cloud transcription remains an explicit, labelled alternative (it is also the only path that exists below the availability floor). Denied/unavailable → typing, with the reason on the card, mirroring the permission pattern of Slice 1.

**Acceptance.** Device **A26**: airplane mode, on a device/OS where the on-device module reports available: tap-record (not hold), speak a reminder, edit one word, submit; a reminder is created and no network request is made (observable via the app's own badges plus device network indicators — not via a proxy claim). **A27**: Speech authorization denied → no recording, copy names Speech in Settings, typing still works. Core: availability/authorization states are typed results, never a silent nil that renders as the cloud offline sentence.

**Plan impact.** New future unit after the planned voice-review unit; it *depends* on that unit's review step, so sequencing is natural. Priority **P2** (P1 for users who cannot type — flagged, not inflated).

### N6. The nudge you cannot act on, snooze, or find again

**Flows.** (a) *Caregiver at the store:* the Arrive nudge "You're out of bread" appears; the useful next actions are "bought it" (clear the fact) and "remind me at home" — neither exists; tapping the notification opens the app to whatever tab was last open, with the fact nowhere highlighted. (b) *Morning brief while the app is in the foreground:* the brief's once-per-day marker is written ([Proactive.swift](../../core/Sources/PocketCore/Proactive.swift:111)) and the notification request is added with `try?` ([AppModel.swift](../../app/PocketGlimmer/AppModel.swift:250)); with no notification delegate registered, a foreground banner is not presented by default, and if authorization was denied the `add` fails silently — in both cases the day's brief is consumed and never seen. (c) Denied notifications generally: Grok's J8 recovery says "still return the brief text to Shortcuts", but the intent's return value is the nudge bodies joined by newline ([Intents.swift](../../app/PocketGlimmer/Intents/Intents.swift:31)) — worth stating in the journey, today unremarked.

**Code.** `Nudge.factIDs` exist precisely to support actionability and are dropped at the app boundary ([Proactive.swift](../../core/Sources/PocketCore/Proactive.swift:30) vs [AppModel.swift](../../app/PocketGlimmer/AppModel.swift:247)). No `UNNotificationCategory`, no response delegate, no deep link, no "mark bought" anywhere in the app.

**Smallest change (future, after journal).** Register one category with "Bought it / Done" and "Snooze" actions carrying the fact ids in `userInfo`; a response handler that forgets or re-times the fact through the same store the Memory tab uses, and records the outcome where the user can see it on next open. Set the morning-brief day marker only after a *delivered-or-visible* outcome is known, or surface "brief ready" inside the app when a trigger fired in the foreground. Keep the no-GGUF split Grok specified; notification actions must not boot the model either.

**Acceptance.** Device **A28**: fire the shopping trigger; from the notification, mark bought; open Memory and confirm the fact is gone; fire the trigger again — no second nudge that day (extends Grok's slice-1 suppression note). **A29**: notifications denied; the automation's returned text still contains the brief (observable in Shortcuts), and the app does not claim a notification was posted.

**Plan impact.** Extends L3 (care routine) in the journeys report; not in the delivery plan's unit table today. Priority **P2**.

### N7. Retention, "forget everything", and what actually survives a deletion

**Flows.** (a) "Forget everything about my daughter." (b) A user who deletes a sensitive fact reasonably believes it is gone. (c) A returning user expects yesterday's conversation; nothing tells them chat is session-only until it is gone.

**Code.** Deletion is one swipe per fact ([MemoryView.swift](../../app/PocketGlimmer/Views/MemoryView.swift:59)); there is no subject-level or all-data deletion, and no view states what persists. Meanwhile telemetry rows store the full decision **context** (the utterance plus retrieved memory text) in the same SQLite file ([Telemetry.swift](../../core/Sources/PocketCore/Telemetry.swift:15), insert at [:69](../../core/Sources/PocketCore/Telemetry.swift:69)); `forget(id:)` deletes only the fact row, so a forgotten fact's text can persist inside logged contexts and inside the user-exported `distillation-queue.jsonl` in Documents ([AppModel.swift](../../app/PocketGlimmer/AppModel.swift:265)) — which Settings already discloses may enter device backups ([:48](../../app/PocketGlimmer/Views/SettingsView.swift:48)). I am not re-opening the privacy repair (other workers own it); the *journey* gap is that "Forget" over-promises, and there is no user-facing retention contract: facts persist, telemetry persists, chat/pending/shares do not, kept voice recordings accumulate in Documents/Recordings with no in-app management ([VoiceCapture.swift](../../app/PocketGlimmer/Capture/VoiceCapture.swift:57)).

**Smallest change (future).** (1) Memory tab: subject-grouped "Forget all about X" and a Settings "Delete all assistant data" with a destructive confirmation, whose scope is enumerated in the copy (facts, corrections, telemetry, exports, recordings) and implemented against exactly that list. (2) One sentence in Memory and in onboarding: conversations and unconfirmed cards are not kept between launches. Both are UI/copy plus store deletions; no model involvement.

**Acceptance.** Core: after subject deletion, `active()`, `history`, corrections and a telemetry context search contain no row for that subject (test at the store layer; the exact telemetry purge rule is the privacy workers' call, but the test must exist). Device: delete-all, force-quit, relaunch — Memory empty, chat empty, and Settings shows no residual export row count.

**Plan impact.** Future; must be coordinated with the in-flight privacy repair so deletion semantics are defined once. Priority **P2** (P1 if the privacy repair's threat model counts forgotten-fact residue as in-scope — that is their call, recorded here as a dependency, not assumed).

### N8. Compound requests finish at most half, silently

**Flow (worker/student).** "Remind me to call the dentist at 5 and text Sam I'm running late." One `route`/`toolChoice` pass picks a single tool ([Assistant.swift](../../core/Sources/PocketCore/Assistant.swift:134)); the other half is neither done nor mentioned. The user discovers the omission when Sam never gets the text. Saved multi-step definitions (contract Slice 2) address *repeated* compounds the user has formalised, not the ad-hoc sentence in front of them.

**Smallest change.** Disclosure before decomposition: when an utterance contains two effect verbs the single-step path cannot both serve, the reply must say which part was acted on and which was not, and stage the second as its own card where the existing parsers can bind it. Full ad-hoc multi-step execution is **not** the small change and should not be smuggled in; the contract's one-claim-per-attempt discipline applies per part.

**Acceptance.** Core: a two-effect fixture turn yields either two staged attempts or one acted result plus an explicit not-done sentence naming the other effect; a test asserts the absence of a silent single `.acted`. **Plan impact:** future; disclosure copy can ride Slice 1's summaries. Priority **P3**.

### N9. The busy sentence eats user data (sharpening of a covered gap)

Grok states that `send` refuses a second request while busy. Three concrete losses follow, unexamined there:

1. **Shared content.** `HandleTextIntent` hands text/file to `send(ask, sharedText:)`; the busy guard returns before `SharedInbox.put`, so the shared body — which exists only in the intent's parameters — is discarded, and Siri/Shortcuts speak the busy sentence as the intent's result ([AppModel.swift](../../app/PocketGlimmer/AppModel.swift:198), [SkillIntents.swift](../../app/PocketGlimmer/Intents/SkillIntents.swift:67)). A user sharing five emails from Mail at the wrong second loses them with no trace.
2. **A finished recording.** `finish()` discards a completed WAV when busy ([VoiceCapture.swift](../../app/PocketGlimmer/Capture/VoiceCapture.swift:114)): the user spoke, the audio existed, and the outcome is a system line.
3. **Intent answers.** `AskPocketGlimmerIntent` returns whatever `send` returns, so a busy collision is spoken as if it were the answer to the question asked ([Intents.swift](../../app/PocketGlimmer/Intents/Intents.swift:41)).

**Smallest change.** Accept-and-stage instead of refuse-and-drop for data-bearing entry points: put shared text in the inbox **before** the busy check (it is a store, not an execution), keep a finished recording as a staged transcript draft, and have intents return an explicit "busy, saved for you" result distinct from an answer. Execution stays single-flight; only the *dropping* changes. This composes with Slice 1 (a staged share is a draft-class row, not an effect).

**Acceptance.** Core/app-level: a busy `send` with `sharedText` leaves `SharedInbox.peek()` non-nil and returns the busy-staged result; the next free turn can consume it. Device **A30**: start a long cloud answer, immediately share text from Mail; the share is acknowledged as saved, not answered-with-busy, and summarises correctly once free.

**Plan impact.** Small; land with Slice 1's staging work. Priority **P1** (data loss, cheap fix).

### N10. Connectivity is not binary

`NWPathMonitor` sets one boolean from `path.status == .satisfied` ([AppModel.swift](../../app/PocketGlimmer/AppModel.swift:73)). Consequences unexamined by Grok: (a) a captive portal or filtered network reads "Online", so voice/camera proceed and fail late with provider errors instead of the honest offline sentence; (b) `isExpensive`/`isConstrained` (roaming, Low Data Mode) are never read, so a traveler can upload a photo or a minute of WAV over a metered link with no warning — Glimpse shows size before sending ([:61](../../app/PocketGlimmer/Views/GlimpseView.swift:61)), voice shows size only *after* ([VoiceCapture.swift](../../app/PocketGlimmer/Capture/VoiceCapture.swift:125)); (c) the registry's `offlineCapable` flag is defined and never consulted (verified: no reader outside [Skills.swift](../../core/Sources/PocketCore/Skills.swift)), so offline guidance cannot prefer the skills that would actually work.

**Smallest change.** Surface constrained/expensive in the composer status and require an explicit tap-through before cloud uploads on a constrained path; consult `offlineCapable` when composing offline explanations ("this one needs internet; these work offline: …"). No routing or model change. **Acceptance:** device **A31** with Low Data Mode on: a Glimpse send warns before upload; a reminder still saves silently. **Plan impact:** copy/state only, any slice. Priority **P3**.

### N11. Accessibility beyond the hold gesture

Grok J16 covers hold-to-talk, a typed equivalent, Dynamic Type and the transcript editor. Three further code-level gaps:

1. **Glimpse "Find" results are visual-only.** The overlay's accessibility is a count ([GlimpseView.swift](../../app/PocketGlimmer/Views/GlimpseView.swift:215)); the chat mirror says "SAM 3.1 outlined N × label" ([GlimpseView.swift](../../app/PocketGlimmer/Views/GlimpseView.swift:111)). A blind user — the person with most to gain from segmentation — gets no per-object list (label, confidence, rough position in words). Smallest change: a text list under the result, generated from the same `[Segment]` values, read as ordinary text. No model call.
2. **The confirm button's hint exposes a raw tool id** — `accessibilityHint("Runs \(p.tool)")` renders values like `skill:whatsapp_send` or `send_message` to VoiceOver ([ChatView.swift](../../app/PocketGlimmer/Views/ChatView.swift:83)). The card should speak the human title and the bound fields (the contract's `reviewSentence` is the right source once Slice 1 lands).
3. **State is colour- and caption-led.** Online/offline is a tinted pill with a correct label (good, [Components.swift](../../app/PocketGlimmer/Views/Components.swift:16)); confidence is accent-vs-orange plus a percentage ([Components.swift](../../app/PocketGlimmer/Views/Components.swift:20)); the live strip has no combined accessibility element ([ChatView.swift](../../app/PocketGlimmer/Views/ChatView.swift:45)). With the planned tap-to-record, also verify the recording state is announced (the current label does change, [VoiceCapture.swift](../../app/PocketGlimmer/Capture/VoiceCapture.swift:95) — keep that behaviour in the tap design).

**Acceptance.** Device **A32**: VoiceOver pass over (i) a pending card (hint must be a sentence, not an id), (ii) a Find result (each object reachable as text), (iii) largest Dynamic Type on the confirm card (no clipped Confirm/Cancel — Grok already lists a large-text pass in its device measurements; this makes it a gate with named screens). **Plan impact:** rides the planned voice/accessibility unit; items 1–2 are small standalone fixes. Priority **P2**.

## 9. Bottom line

Grok's report is substantially right about the architecture of failure — volatile state, unjournalled effects, handoffs masquerading as outcomes — and the shared contract is the right shape for fixing it. What it missed is a layer of *everyday correctness* failures that survive even a perfect journal: a disambiguation the code itself discards (N1), the family names people actually say (N2), parsed-but-wrong times (N3), the impossibility of fixing yesterday's entry (N4), an offline voice capability the platform already offers (N5), nudges with no next action (N6), and a "Forget" that does not forget everywhere (N7). Two of these (N1, N9, and the instant-display half of N3) are cheap enough to fold into Slice 1's acceptance now; the rest are honestly future work and are sequenced above so none of them quietly becomes a second, weaker recovery path beside the contract's.
