## 0. How a request becomes an effect today (traced end-to-end)

1. UI / Intent entry: `ChatView` Send button -> `AppModel.send(_:sharedText:source:)` [baseline-AppModel.swift:198]; `AskPocketGlimmerIntent`, `RunSkillIntent`, `HandleTextIntent` (all `openAppWhenRun=true`) also call `AppModel.send`; `ProactiveTriggerIntent` (`openAppWhenRun=false`) -> `AppModel.handleTrigger` -> `ProactiveEngine.handle` -> `UNUserNotificationCenter.add` [baseline-AppModel.swift:243-254].
2. `AppModel.send` guards `!busy` (single-flight, returns "I'm working..." string instead of queueing), puts shared text into process-global `SharedInbox` (900s in-memory), appends user `ChatItem`, sets `busy=true`, calls `Assistant.handle(text)` [baseline-AppModel.swift:199-207]. `chat`, `busy`, `ChatItem.pending: PlannedAction?` are in-memory `@Observable` state; only `onboarded` touches UserDefaults. SQLite `pocket.sqlite` in ApplicationSupport holds `MemoryStore` facts/corrections/meta + `TelemetryLog` decisions. No action/attempt table exists.
3. `Assistant.handle` [baseline-Assistant.swift:100]: memory write (`rememberOrNot` -> `RuleFactExtractor.extract` -> `MemoryStore.upsert` with `memoryConflict` resolver that *awaits* Reflex between read and write), then `route` decision, then optional `skillOverride` (explicit app words), then `toolPath` or local/cloud answer. Sensitivity gate only on escalate/local-sensitive paths.
4. Tool path: `toolChoice` -> either `planSkill` (registry skills) or six trained tools. Args are regexes (`ArgumentExtractor.heuristic`, `SkillArgs.extract`). Contact/event disambiguation via `contactPick`/`eventPick` over display strings (max 7 + ask). `confirmBeforeAct` + hard rules produce `Reply.needsConfirmation(PlannedAction, prompt:)` or immediate `.acted(try await execute(action))` / `actions.perform(action)` [baseline-Assistant.swift:186-236, baseline-ActionPlanner.swift:99-183].
5. `Assistant.execute` dispatches: non-`skill:` -> `ActionExecutor.perform`; `skill:` -> re-lookup `skills.skill(id:)` *at execute time*, then `executorTools` native -> `SystemActions.perform(PlannedAction(tool:h,...))`, `email_digest` (takes SharedInbox), `analyze_document` (takes SharedInbox or picker then `reason`), `html_viz`, `cloudReason` (`reason`), default -> `SkillRunner.run` [baseline-ActionPlanner.swift:145-183].
6. Executors return only `String`. `SystemActions.perform` [baseline-SystemActions.swift:49-109]: EventKit saves discard identifiers; compose sheets via `ComposeSheets` singleton continuation; fallbacks sms:/mailto:/shortcuts:// via `ComposeSheets.open` (UIApplication.open Bool). `IOSSkillRunner.run` [baseline-SkillRunner.swift:19-39]: `.urlScheme` (clipboard side-effect first, then open), `.shortcut` (open shortcuts://), `.native` handlers, `.cloudReason` stub. Results flow back as `Reply.acted(String)`; `AppModel.send` renders any acted string identically with badge "on device · X ms". `AppModel.confirm` clears `chat[i].pending=nil` *before* `await assistant.confirm(a)`, sets busy, maps thrown errors via `try?` to literal "Failed" [baseline-AppModel.swift:233-240]. `cancel` only clears pending.
7. Proactive path: `ProactiveEngine.handle` iterates `memory.active()` x rules, Reflex `nudgeNow` gate each pair, returns `[Nudge]`; morning brief gated by `memory_meta[last_morning_brief]` day string set *after* gate, *before* notification post [baseline-Proactive.swift:93-128].

## 1. Persistence boundaries (what survives process death, what does not)

- Survives: Memory facts/corrections/meta, Telemetry decisions (incl. raw `context` = utterance+memories), skill JSON files (bundle + Documents/Skills/*.json re-read each boot), Keychain keys, UserDefaults flags, distillation export file if user exported. SQLite is one connection, `WAL` + `FULLMUTEX`, `NSRecursiveLock` [baseline-SQLiteDB.swift:17-27]; `transaction` is `BEGIN IMMEDIATE`...COMMIT/ROLLBACK but re-entrancy/deadlock and `exec` inside transaction holding same recursive lock needs checking (lock is recursive, so nested `run`/`query` inside `transaction` body do not deadlock, but `transaction` itself calls `exec` which re-locks — OK only because recursive).
- Does NOT survive: `ChatItem.pending` confirmation cards, `AssistantTurn.action`, `SharedInbox` item, `ComposeSheets.pending`/`DocumentPicker.pending` continuations, `busy`, chat history, in-flight `handle`/`execute`. Kill during compose sheet, during EventKit save, or between plan and confirm = total loss with no tombstone. User must reconstruct from memory/other app.
- Skill definitions are NOT versioned/snapshotted: `SkillRegistry` is rebuilt at boot from current JSON; a `PlannedAction(tool:"skill:<id>", args:)` stores only id+args. `execute` re-resolves id -> current Skill. Edit JSON (or replace bundle) between prompt and Confirm (or across restart) silently changes invocation template/handler/category/confirm semantics under an already-approved prompt. Same for six-tool `PlannedAction`: args only, no definition version at all.
- Contact identity is NOT persisted as `CNContact.identifier`: `searchContacts` returns "[given family] (job, org)" strings (prefix 7) [baseline-SystemActions.swift:21-29]; `contactPick` returns a label string stored into `args["contact"]`; executors re-resolve by `unifiedContacts(matching: CNContact.predicateForContacts(matchingName:))` `.first` [SystemActions.swift:114-120, SkillRunner.swift:71-77]. This is a name re-lookup, not an identity binding.

## 2. Independent issue hypotheses (to stress-test against Grok contract)

### A. Claim / no-replay / crash / concurrency / cancellation
- A1 No durable claim: two concurrent `Assistant.confirm(samePlannedAction)` calls both execute (no in-core guard; only AppModel UI clears pending + busy). App Intent + UI, or double programmatic confirm, duplicates EventKit writes/messages-sheet presentations. `ComposeSheets` singleton `pending==nil` guard turns second concurrent compose into silent fallback (sms:/Shortcut) instead of queue/reject — channel substitution under concurrency.
- A2 Crash window: EventKit `save(commit:true)` succeeds, process dies before string returns / before UI appends acted bubble -> no record; user re-asks -> duplicate reminder/event. No idempotency key, no identifier, no read-back dedup. Same for clipboard+open and Shortcut handoff.
- A3 Cancellation is not wired: Swift Task cancellation is never checked in `handle`/`execute`/runner; `AppModel.cancel` only clears pending pre-execution. Cancelling while compose sheet or picker is up leaves continuation dangling until delegate; backgrounding/kill loses it. No timeout on `withCheckedContinuation` awaits.
- A4 `MemoryStore.upsert` read-await-write race admitted in its own comment [baseline-Memory.swift:93-96]: two concurrent upserts of same subject+attribute can both insert; `consolidate()` later merges. On single-MainActor app path this is masked; intents/background would expose it. Need to check if contract claims exactly-once for memory too.

### B. Typed evidence vs String
- B1 Every executor returns human `String` ("Opened...", "Handed to Shortcut...", "Reminder set:...", "Messages accepted..."). No enum distinguishes opened/handed-off/accepted/queued/cancelled/failed/unknown. `AppModel` cannot branch, journal, or compensate; copy edits masquerade as semantics. `MFMessageComposeViewController` result `.sent` is collapsed to text inside delegate and the typed value is thrown away [baseline-SystemActions.swift:185-212]. Delivery vs acceptance vs queueing distinctions survive only as wording.
- B2 `UIApplication.open` Bool is the *only* evidence for URL/Shortcut skills, including money-spending (`uber_ride`), playback (`appletv_play`), alarms/timers/notes via Shortcuts. Bool = system accepted URL, not Shortcut exists/ran/effect happened. Code is honest in strings ("Handed to... · if it isn't installed, Shortcuts will say so") but type system/UI badge treats it as `.acted`.

### C. Immutable snapshots & catalog versions
- C1 See §1: approved `PlannedAction` is not bound to Skill bytes/hash/version, ArgSchema, or catalog version. User JSON override (`SkillRegistry.merge`: later id wins [baseline-Skills.swift:197-202]) can retarget an id between approval and execution, or between app versions.
- C2 Category authority leak: JSON controls `category`; hard rule only forces confirm for message/social/email. A user/attacker JSON redefining e.g. `alarm_create` or a new id with category `device`/`web`, invocation `url`/`shortcut`/`native`, `confirm:false` executes without confirm whenever `confirmBeforeAct` says act. Conversely redefining built-in `imessage_send` id to category `web` + url template would bypass the "messages always confirm" hard rule because rule keys off attacker-controlled category, and `executorTools` routing keys off handler string in JSON. `native` handler names are arbitrary strings from JSON dispatching into code handlers (`autoreply_rule` writes memory!). No allowlist/signature/argument allowlist. This is a confused-deputy / prompt-injection-to-file amplifier: any flow that writes Documents/Skills/*.json (share sheet? Shortcut? user pasting Muse output?) gains effect authority.
- C3 `open_url` skill: template `{url}` with `raw` insertion (no percent-encoding) + `URL(string:)` + `UIApplication.open` — a model/user-supplied arg can invoke arbitrary schemes (tel:, sms:, shortcuts://, settings deep links?) subject only to skillPick+confirm. JSON-supplied templates likewise unbounded (any scheme/host, `{phone}` injection, clipboard template). No scheme/host allowlist in `IOSSkillRunner.openURLSkill`.

### D. Contact identity revalidation
- D1 Name-string identity + `.first` re-lookup: two "Sam Lee" contacts, renamed contact, contact deleted/merged, limited-access set change between pick and confirm -> wrong recipient or silent first-match. `displayName` strips " (..." hint, discarding the disambiguator the user saw. `addresses(for:).phones.prefix(1)` picks first phone arbitrarily (iPhone vs home). No revalidation prompt on mismatch at confirm/execute time; no `CNContact.identifier` stored in PlannedAction.
- D2 `searchContacts`/`searchEvents` breadth: prefix(7) truncation can hide the intended person/event; `contactPick` fallback is `ask` but plain `toolPath` clarify string loses the candidate set state — next utterance is a fresh `handle`, so "the second one" / "Sam Ortiz" as a reply is re-planned from scratch (may re-trigger remember/route/tool). Disambiguation is not a resumable state machine.

### E. Exact trigger semantics (Proactive)
- E1 `Trigger` is unauthenticated data from any Shortcut automation calling `ProactiveTriggerIntent` (kind/place/sender/text are Shortcut-supplied strings). Rules match by regex/substring: `promise-when-messaged` uses `(sender).lowercased().contains(f.subject)` — subject "sam" matches "Samantha"/"sam@evil"; place regex matches substring anywhere. A Shortcut (or anything that can invoke the intent?) can fabricate a trigger to surface nudges (low severity, nudge only, but it displays memory contents in notifications — privacy leak to lock screen?). `Nudge` fact text rendered into `UNNotification` body without sensitivity check.
- E2 Morning brief idempotency uses local day string `MemoryStore.day` (yyyy-MM-dd current tz) in `memory_meta`; timezone travel / clock change can double-fire or suppress. `setMeta` happens before `UNUserNotificationCenter.add` (which is `try?`-swallowed in AppModel) — failed post still consumes the day. Other nudges have NO dedup/cooldown at all: every matching trigger re-nudges.
- E3 `ProactiveTriggerIntent` boots full GGUF via `AppModel.boot` even for morning brief which needs only SQLite+EventKit lines; background/locked execution budget likely exceeded — device-unverified but architecturally suspect.

### F. Multi-step completion meaning
- F1 Baseline has no multi-step: one PlannedAction per turn. Any workflow/chain built on `execute` returning String cannot define partial completion, ordering, or stop-on-failure. `HandleTextIntent` chains share->send; email_digest/analyze consume SharedInbox via `take()` BEFORE `reason()` runs — if `reason` throws/escalates-offline or user cancels downstream, shared payload is already consumed and unrecoverable. `html_viz` uses `peek()` (inconsistent). Ordering bug candidate: `analyze_document` takes inbox text first, only calls picker if empty — stale share (up to 15min) silently wins over explicit "analyze this document" picker intent? Actually code prefers shared text over picker, which may be wrong document.
- F2 `autoreply_rule` native handler writes Memory inside SkillRunner as side effect of `run` [baseline-SkillRunner.swift:102-110] — an effect executed via planner confirm path but also directly runnable; memory write is not journaled as the effect, and returned string admits Instagram cannot be automated yet still says "Saved". Completion meaning muddy.

### G. Shortcut callback spoofing/replay (future surface)
- G1 Baseline has NO callback: no `CFBundleURLTypes`, no `onOpenURL`, entitlements empty, `SkillTemplate.shortcutURL` uses plain `shortcuts://run-shortcut` without x-callback [baseline-Skills.swift:164-167]. Therefore today spoofing is moot — but any contract adding `pocketglimmer://` x-success must face: custom schemes are claimable by any app and invocable by any app/website; parameters are attacker-controlled text. Token must be unguessable, single-use, attempt-bound, expiry-checked, and result treated as untrusted Shortcut-authored text, never as OS attestation. Universal Links would need associated-domains + hosted AASA + domain — heavier but authenticated delivery channel (still must validate params). Need official citations (fetched below pre-contract: Apple Shortcuts guides + custom scheme docs).

### H. Planner boundary
- H1 Planner is regex + one-letter Reflex picks (route/toolChoice/skillPick/contactPick/confirmBeforeAct/sensitivity) with τ=0.90 frozen. It is NOT a sandbox: `SkillArgs.extract` fills args by regex from raw utterance; model only picks among retrieved skills. Risks: retrieval (BM25+hash cosine, threshold 0.6, 0.3*top filter) can surface wrong skill; `explicitSkill` word-override table and `isExplicitRequest` word list are string matching that user text can game to bypass trained tool path; `confirmBeforeAct` context includes arg values (prompt injection via body/contact strings into the 1B's confirm decision — though hard category rule backstops messaging). Planner must never be able to invent invocation/handler/category — today registry JSON already violates this (see C2).
- H2 `searchEvents` predicate bug: `.filter { titleWords.contains { q.contains($0) } }` checks query-contains-title-word (reversed) [baseline-SystemActions.swift:36] — "when is my dentist appointment" vs title "Dentist" works, but "dentist" query vs "Annual dental cleaning" fails, multi-word queries behave oddly. `find_event` then relies on this.
- H3 Date handling: `SystemActions.date(from:)` = first `NSDataDetector` date match, locale/tz implicit; `create_event` defaults missing parse to `now+1h` and 1h duration without confirm [baseline-SystemActions.swift:61-68] — a vague "schedule lunch with Leo" writes a real event at guessed time. `create_reminder` silently drops missing date. Raw phrase strings pass to Shortcuts for alarm/timer parsing (device-dependent).

### I. Compensation
- I1 No compensation possible: EventKit identifiers discarded, messages/URLs/Shortcuts have no inverse, Memory autoreply write has no linked undo (though fact delete exists manually). Any contract promising rollback must be limited to identified EventKit deletes + memory row deletes with re-read equality check; sending/ride/playback cannot be compensated.

### J. Edit/approve races & usability
- J1 Confirmation card is a static prompt string + Confirm/Cancel buttons [baseline-ChatView.swift:79-84]; no editable recipient/body/title/time fields. Correcting a low-confidence message requires re-uttering from scratch (losing args). Between prompt and tap: contacts/calendar/registry/network can change; no staleness warning, no expiry, no diff of "what will run now" vs "what was shown". `AppModel.confirm` uses captured `PlannedAction` verbatim (good for snapshot of args, bad: no revalidation).
- J2 Errors collapse: `confirm` catch -> "Failed" (loses EventKit permission vs save error distinction); `SystemActions.requestAccess` uses `try?` and discards denial [baseline-SystemActions.swift:15-19]; permission state never checked before save, so denial surfaces as generic failure or empty contacts ("I couldn't find X" when actually limited/denied). `canSendText/canSendMail == false` falls through to sms:/mailto:/Shortcut chain — user intent (sheet) silently downgraded.
- J3 Clipboard: URL skills write body to general pasteboard BEFORE open succeeds and never clear it [baseline-SkillRunner.swift:50-54]; failure leaves message text on clipboard. Also `instagram_dm`/`x_dm` require paste in other app — completion is manual and unobserved.
- J4 Single `busy` gate rejects (not queues) concurrent user/Shortcut requests; voice finish path has multiple busy rechecks that can drop a recording already sent to transcribe ("Another request is in progress. The recording was not sent" — but audio WAS sent for transcription before this check? trace: `gate.transcribe` runs under `model.busy=true` set locally, so check after is about send, wording may mislead). Voice transcript auto-sends via `model.send(t.text)` with NO edit/review step — a mis-transcription becomes a planned action/confirmation; hold-to-talk with no review is a usability/safety gap for message skills. Camera glimpse similar (sensitivity gate only).

### K. Simplicity challenge (pre-contract)
- K1 If contract proposes separate WorkflowDefinition/Run/Step/Attempt/Receipt object graphs + JSON authoring + callback tokens + compensation for every skill, suspect over-engineering for Slice 1. Smallest coherent kernel preserving invariants might be: one durable `ActionAttempt` table (id, idempotency key, frozen PlannedAction + skill hash + contact identifier + state enum + typed outcome + EventKit identifier), one claim via SQLite transaction (`BEGIN IMMEDIATE` + unique constraint), and typed `ActionOutcome` enum replacing String at PocketCore boundary (String rendering at UI edge only). Defer general multi-step DAG until a single-step journal is proven on device.

## 3. Official-source checks done BEFORE reading Grok contract (retrieved 2026-11-04)
- Shortcuts run URL: `shortcuts://run-shortcut?name=&input=&text=` runs a shortcut already in collection; no result. Apple Support "Run a shortcut using a URL scheme" https://support.apple.com/guide/shortcuts/run-a-shortcut-from-a-url-apd624386f42/ios (fetched full text; iOS 27 guide version selected).
- x-callback: `shortcuts://x-callback-url/run-shortcut?...&x-success=&x-cancel=&x-error=`; x-success appends `result` = shortcut's textual output; x-error appends `errorMessage`; x-cancel provides no output. Apple Support "Use x-callback-url with Shortcuts" https://support.apple.com/guide/shortcuts/use-x-callback-url-apdcd7f20a6f/ios (fetched full text). Implication: result is shortcut-authored text, not OS attestation.
- MessageUI/Mail/UIApplication.open/EventKit developer pages fetched (JS-rendered, body not extracted by fetcher) — URLs reserved for citation: https://developer.apple.com/documentation/messageui/messagecomposeresult , https://developer.apple.com/documentation/messageui/mfmailcomposeresult , https://developer.apple.com/documentation/uikit/uiapplication/open(_:options:completionhandler:) , https://developer.apple.com/documentation/eventkit/accessing-the-event-store . Semantics to be corroborated via search snippets + known API contracts; marked as needs-full-text verification in final report if fetcher stays empty.
- Custom scheme vs Universal Links (search-corroborated, Apple docs): custom schemes can be registered by any app, conflicting scheme winner undefined; Universal Links require Associated Domains entitlement + hosted apple-app-site-association, only domain owner can authorize. Apple: "Defining a custom URL scheme for your app" https://developer.apple.com/documentation/uikit/core_app/allowing_apps_and_websites_to_link_to_your_content/defining_a_custom_url_scheme_for_your_app and "Allowing apps and websites to link to your content" https://developer.apple.com/documentation/xcode/supporting-universal-links-in-your-app (via proxy mirror text). Treat callback-via-custom-scheme as unauthenticated.
- AlarmKit: iOS 26+ framework, `AlarmManager.shared.requestAuthorization()`, `NSAlarmKitUsageDescription` required, no special entitlement (corroborated by multiple secondary sources citing Apple docs/WWDC25; official page https://developer.apple.com/documentation/alarmkit to be cited as availability iOS 26.0+ — NOT yet directly fetched successfully; flag unresolved).
- EventKit iOS 17+ granular: `requestFullAccessToEvents/Reminders` vs write-only (events only); full required to read back. Contacts limited: `CNAuthorizationStatus.limited` = user-chosen subset (iOS 18 two-stage prompt per secondary sources; official https://developer.apple.com/documentation/contacts/cnauthorizationstatus/limited ). Both need device verification for Pocket Glimmer's exact request calls (`requestFullAccessToReminders/Events` exist in code).
