## Overview

Pocket Glimmer's shipped "System 1" (Reflex) is a 13-way typed multiple-choice classifier, not a general assistant. `core/Sources/PocketCore/Decision.swift:5-19` defines twelve trained types plus untrained `skillPick`. Each decision is one forward pass that reads logits over the option-letter tokens (`Decision.swift:3-4`). The shipped student is Llama 3.2 1B Instruct + LoRA r16, one epoch over 892 Muse Glimmer teacher rows, merged and quantized to Q4_K_M (`eval/results/AFTER_FLOOR.md`; `models/README.md` SHA-256 `a5c60a88…82c2`).

Round 2 tried to scale labels with Muse Spark Open votes on Baseten, expanded the train file to 2,915 rows, and swept LoRA variants on Modal. Its best candidate, V4 on the sharpened `r2c` file, improved the nominal cal180 calculation and coverage but failed the pre-registered ECE clause on warm-server repeats, so ep1 stayed shipping (`eval/results/ROUND2.md:26,59-64`). The current pool still holds 6,455 unlabeled contexts that could be labeled, but row count is not independent-task count, and `r2a` vs `r2c` changed target construction as well as mixture, so the saved comparison does not isolate a data-quantity effect (`ROUND2.md:65,74`; `docs/training/SCALING_RUN_2026-11-04.md`).

The chain that must be grounded before spending is: scenario pool → dedupe guard → teacher labeling (true logits vs sampled votes) → soft-target construction (including vote imputation) → LoRA loss at the answer-letter position → merge/quantize → deployed readout (few-shot prompt + contextual prior + tau gate) → calibration arithmetic → gate. Each stage has a distinct failure mode. Scaling only rows, only epochs, or only compute without fixing target definition, prompt alignment, and evaluation separation will repeat the round-2 confound at higher cost.

## How It Works

### 1. Scenario pool (contexts without trusted labels)

`training/pg_train/scenarios.py:118-147` generates seeded synthetic contexts for the twelve types from small name/place/item/task tables, with a 15% situational envelope (`_envelope`, `scenarios.py:127-131`). Its `hint` is the generator's intended answer and is explicitly "sanity stats only; labels come from teachers" (`scenarios.py:1-2`). A separate `nudgeNow` v2 generator (`scenarios.py:167-198`) covers store/person/time triggers the v1 generator misses.

`training/data_scale/build_pool.py:14-15,29-41` builds the 8,245-row scale pool: weighted synthetic draws (nudgeNow 1,800 down to sensitivity 250) plus public train-split utterances wrapped in the same envelopes — MASSIVE en-US train, CLINC150 plus train, SNIPS train. It capitalizes the first character and adds `User:` / `Network:` headers; original dataset annotations are discarded. The CLINC OOS *test* split becomes `clinc_oos_test_stress.jsonl` and is never trained on (`build_pool.py:57-61`).

Scale fact: a "row" is one rendered context. Synthetic rows share generator templates and vocabularies, and CLINC contributes 1,000 unique OOS utterances rendered twice in the stress set (`docs/EVALUATION_CLAIMS.md:38`). Counting rows overstates independent coverage; splits must group by source-family and near-duplicate cluster, not by row.

### 2. Dedupe guard (frozen-eval protection)

`training/local_teacher/dedupe.py:29-57` loads every `eval/**/*.jsonl` row with a `context`, normalizes (lowercase, digits→0, strip punctuation), and drops a training row on exact normalized context or utterance match, or char-5-gram Jaccard ≥ 0.8 on context, or on utterance when longer than 12 chars. `build_pool.py:49-54` applies it plus self-dedupe on `(type, normalized context)`; the saved report shows 1,349 self-dupes and 256 eval-dupes dropped, leaving 8,245 kept (`training/data_scale/out/dedupe_report.json`). `build_round2.py:54-57` re-checks against all eval items and asserts no overlap with cal180 contexts or `gold_all` contexts. `label_round2.py:32` refuses any input whose filename contains "test".

Limit: Jaccard 0.8 on 5-grams catches near-copies of gold wording. It does not make synthetic families independent of gold; gold itself is 300 hand-authored items by one person, 15 cal + 10 report-only per type (`docs/EVALUATION_CLAIMS.md:16`; `eval/gold/gold_calibration.jsonl` 180, `gold_test.jsonl` 120). Template-level leakage (same generator shapes, different surface words) survives the guard by design and must be handled by family-separated evaluation, not by a stricter threshold alone.

### 3. Teacher labeling — two different objects called "soft"

**Glimmer (true logits, local, free).** `training/local_teacher/glimmer_teacher.py:25-55` serves Muse Glimmer 30B IQ2_M behind llama-server, forces the assistant onto `Answer:` with reasoning skipped, reads `n_probs=50`, merges letter tokens, and renormalizes over valid letters. `label_local.py:31-49` appends one flushed+fsynced JSON line per item and skips done ids. `build_train.py:9-16` drops rows with letter mass < 0.5, weights rows by per-type QC agreement, and drops low-confidence rows on imperfect-QC types. Result: 892 rows in `training/local_teacher/out/distill_train.jsonl`, mean top-probability 0.938. These `soft` values are a single forward pass's letter distribution — genuine teacher probabilities (IQ2_M-quantized teacher, so already an approximation of the bf16 Glimmer).

**Spark Open (sampled votes, Baseten, paid).** Baseten returns no logprobs for Spark Open (`training/pg_train/teachers.py:125-128`; `training/spark_teacher/label_spark.py` header), so `label_round2.py:74-123` draws `k` chat completions at temperature 1.0, `reasoning_effort: low`, parses the last standalone letter, and stores raw `votes` (including `None` for errors/unparsed). Adaptive stopping draws `k0` first and tops up to `k` only if not unanimous (`label_round2.py:103-107`); the round-2 run used k0=2→k=5, mean k=2.48 (`ROUND2.md:9`). Per-type caps and a weak-type-first interleaved order keep a partial run balanced (`label_round2.py:19-21,49-55`). Output: 1,790 items in `labels_round2.jsonl`, 1,750 kept after filtering.

These two `soft` fields are not the same quantity. Glimmer's is P(letter | context) from one pass. Spark's (after `build_round2.py`) is a smoothed vote frequency from 2–5 samples. Training code consumes both through the same `r["soft"]` key (`lora_r2.py:84`), so teacher identity is a hidden mixture variable unless `src`/`teacher` is stratified. `lora_r2.py:67-71` can reweight Glimmer rows (`--glimmer-weight`) and confidence-weight rows (`--conf-weight` uses `teacher_conf` = top-vote share for Spark, top prob for Glimmer, `build_round2.py:41`, `build_round2.py:51`), but the default floor recipe treats them identically.

### 4. Soft-target construction and vote imputation

`build_round2.py:27-41` (`spark_row`) builds each Spark target as `(count + alpha) / (validVotes + alpha * nOptions)` with `alpha=0.5` by default, drops rows with < 2 valid votes or top-vote share < 0.6 where share counts *all* draws including failures (`build_round2.py:35`). The three shipped train files share the same 2,915 ids and the same hard `target` (verified: 0 target diffs between `r2a` and `r2c`); they differ only in `soft`:

| File | alpha | impute_k | Spark-r2 mean top-prob | Overall mean top-prob |
|---|---|---|---|---|
| `r2a_train.jsonl` (2,915) | 0.5 | 0 (none) | 0.704 | 0.792 |
| `r2b_train.jsonl` (2,915) | 0.5 | 5 | 0.819 | 0.861 |
| `r2c_train.jsonl` (2,915; SHA-256 `afcf82d7…d3b3`) | 0.1 | 8 | 0.956 | 0.951 |

Imputation (`build_round2.py:31-32`): if a row stopped early with all observed votes equal, replicate the single observed letter to `impute_k` votes. In `r2c`, 1,530 of 1,750 Spark-r2 rows were imputed to k=8 (per-type counts in `build_stats_r2c.json`). A 2-vote unanimous row (target top ≈ 0.71–0.83 in `r2a`, the under-confidence noted at `ROUND2.md:21`) becomes an 8-vote unanimous row with top ≈ 0.9+. No new teacher information is added; the target's implied sample size and sharpness are inflated. The justification recorded in code (`build_round2.py:19-20`) is the Nov-1 k=8 statistic P(votes 3–5 agree | votes 1–2 agree) = 850/866 = 0.982 — that supports predicting the *eventual majority letter*, not treating the sharpened frequency as the teacher's calibrated probability. Any `r2a` vs `r2c` quality difference therefore mixes (a) less Laplace smoothing and (b) imputed sharpness; it is not a data-scale effect. `ROUND2.md:74` says the same: mean top-probability 0.704 → 0.956 with identical row count.

### 5. LoRA training (loss at one position)

`training/round2/lora_r2.py` is the round-2 trainer; `training/local_teacher/lora_gpu.py` is the floor original with identical default math (`lora_r2.py:1-12`). Mechanics:

- Base `unsloth/Llama-3.2-1B-Instruct` (ungated mirror of `meta-llama/Llama-3.2-1B-Instruct`), bf16, LoRA r16/alpha16 (scale 1.0), all-linear targets, dropout 0 (`lora_r2.py:56-57`). Flags vary rank, lr, epochs, `--ce-weight`, `--label-smooth`, `--conf-weight`, `--glimmer-weight`, `--entropy-bonus`.
- Prompts are rendered **zero-shot** (`lora_r2.py:80`: `prompts.llama3(s, context, "zeroShot")`). Only the last position's logits over the valid letter tokens are used (`lora_r2.py:81-84`).
- Per row: `q` = renormalized `soft` (optionally smoothed), `kd = -(q · logSoftmax(student letters))`, `ce = -log p(hard target)`, `term = kd + ceWeight * ce` (+ optional entropy bonus `b * sum(p log p)`), scaled by `row_weight` (`lora_r2.py:67-71,82-89`). Default `ceWeight=0.5` is the floor recipe. Note `-(q·log p)` equals KL(q‖p) plus the constant H(q); minimizing it is cross-entropy to the teacher distribution. With vote-frequency `q`, the "KL" is to an empirical 2–5-sample histogram, not to teacher token probabilities — the proper-loss distinction that matters for calibration: the student is rewarded for reproducing vote sharpness (including imputation sharpness), not teacher uncertainty.
- AdamW, 10-step warmup + cosine to 0, batch 8, seed 0, shuffle seed 0 (`lora_r2.py:58-61`). Steps = ceil(rows * epochs / bsz); 2,915 rows = 365 steps/epoch (Modal logs). Early abort only at step 4 if projected time exceeds `--max-hours` (`lora_r2.py:95-96`).
- Built-in readout is zero-shot on `gold_calibration.jsonl` (`lora_r2.py:41-51,98`), explicitly "NOT the v2+cc headline" (`lora_r2.py:11-12`). It is a training-side diagnostic on the selection set and must never be quoted as the deployed metric.

`training/pg_train/sft_unsloth.py:13-24` is the older hard-label SFT path (loss only on the answer-letter token, labels -100 elsewhere). It is *not* the round-2 path; conflating "SFT" with the soft-target LoRA above hides the target-quality question.

### 6. Export (merge → f16 GGUF → Q4_K_M)

`training/round2/modal_round2.py:42-76` (`_train`) runs the trainer, merges the adapter in fp16, converts with pinned llama.cpp `13ec8f6…` `convert_hf_to_gguf.py --outtype f16`, quantizes `llama-quantize … Q4_K_M`, and records the GGUF SHA-256 and byte size. The shipping ep1 file went through the same merge/quantize shape (`QUANT_IDENTITY.md:5-6`). Quant identity matters: the headline numbers come from the Q4_K_M GGUF through llama-server, not from bf16 PyTorch (`QUANT_IDENTITY.md:4-8`), and the quant ladder shows Q8_0/f16 do not beat Q4_K_M on the cal bound while Q3/Q2 degrade (`QUANT_IDENTITY.md:29-33`). Any candidate must be compared as an exact GGUF, byte-identical file, not as an adapter or bf16 checkpoint.

### 7. Deployed readout (what the phone actually computes)

`core/Sources/PocketCore/Reflex.swift:40-58`: render prompt with `profile.promptStyle`, get next-token logits for the candidate letters, floor unseen letters at `min - 2`, subtract the per-set contextual prior if present, softmax with `profile.temperature` (shipping: empty → T=1, `Calibration.swift:3-4`), take argmax confidence, escalate to the fallback iff `conf < tau` (shipping `defaultTau=0.90`, per-type tau empty). The bundled profile asserts `promptStyle == .fewShot`, `defaultTau == 0.90`, finite priors for every static and dynamic set (`app/PocketGlimmer/AppModel.swift` `bootOnce` guard; `app/PocketGlimmer/Resources/Models/calibration.json`).

So the **deployed** student is evaluated few-shot with prior correction, while it was **trained** zero-shot without priors. `Decision.swift:157-160` documents the intent (few-shot for the untrained base, zero-shot for the distilled student), but the shipped profile still selects few-shot. This is a live prompt mismatch: training distribution ≠ deployment distribution. It may help (exemplars + prior debiasing) or hurt (longer prefill, exemplar bias); round-2's own trainer readout (zero-shot) vs headline readout (v2+cc few-shot + LABELS_V2 relabeling + cc) already differ, and `eval_round2.py:28` calls the headline chain with `R.run(rows, "v2", True, 0.8)` — variant v2 relabels option text via `LABELS_V2` and adds cc (`eval/experiments/run_prompt_variants.py` `relabel`/`render`/`cf_logp`). Three renderings are in play: (i) trainer zero-shot canonical labels, (ii) headline v2+cc few-shot relabeled + prior-corrected, (iii) phone few-shot canonical labels + stored priors. "Prompt alignment" is therefore a first-class experimental factor, not a detail. The scaling record flags it as a separate hypothesis (`SCALING_RUN_2026-11-04.md`).

### 8. Calibration arithmetic and what it cannot claim

ECE (10 bins) is computed on raw letter-softmax confidences; there is **no temperature scaling in the shipping pipeline** (`QUANT_IDENTITY.md:8`; `Calibration.swift:3-4` "shipped profile uses T=1"). `pg_train/calibrate.py:19-26,56-87` *can* fit a temperature and per-type tau on held-out student logits, but that fitted profile is not what ships.

The LTT/conformal numbers: `conformal.py:35-59` and `Conformal.swift:56-99` implement the exact binomial p-value `P(Bin(n_tau, alpha) <= k_tau)` per tau on the fixed 99-point grid with Bonferroni level `delta/K`, plus `tightest_bound` (smallest Clopper–Pearson upper bound across the grid). For 0 errors in 64 accepted, `1 - (0.1/99)^(1/64) = 0.10217` (`docs/EVALUATION_CLAIMS.md:20-22`). Both implementations agree.

Why the nominal bound is not a certificate here: Learn Then Test assumes a *fixed* model and i.i.d. calibration draws [LTT primary source]. Cal180 (180 hand-authored, stratified 15/type) selected the teacher, epoch, quantization, prompt, and threshold; the 99-way correction covers thresholds only (`EVALUATION_CLAIMS.md:24`). The sets are not a random sample of phone traffic (`EVALUATION_CLAIMS.md:16`). At the shipped tau 0.90 the report-only split gives 3 errors in 44 accepted → nominal one-sided 90% upper limit ≈ 14.6% (95%: 16.7%), also assumption-dependent (`EVALUATION_CLAIMS.md:28`). Cal180 nominal bounds must be reported as "nominal calculation on the selection set" with fresh/warm state, never as guarantees. Prior cal-based selection and repeated test120 exposure (13 saved report-only files, `EVALUATION_CLAIMS.md:16`) mean neither split can serve as an independent certification for a new candidate.

### 9. Inference-state noise (why single runs mislead)

llama-server prompt-cache/slot numerics make identical prompts non-deterministic across server state. Evidence: QUANT_IDENTITY re-run of the same shipping GGUF changed 4/180 cal and 2/120 test predictions, max confidence delta 0.08, band ≈ ±0.01 acc / ±0.01 ECE / ±0.5pt bound (`QUANT_IDENTITY.md:27`). PERM_AVG's six single-order passes span ECE 0.040–0.056 and bound 10.4–10.9%; the first pass after server start differs from later passes on 7/180 predictions (`PERM_AVG.md:45-49`). Round-2 finalists: V4 fresh ECE 0.059 vs warm 0.066 (the 0.006 gate margin), SHIP fresh 0.040 vs warm rep4 0.052 (`ROUND2.md:59,62`). `eval_round2_reps.py` exists precisely to separate fresh (pass 1) from warm (passes 2+) on one server. Any gate that does not fix server state, thread count (`-t 4`, `-c 4096` in `eval_round2.py:18`), GGUF SHA, and pass index will chase noise. Permutation averaging is a *different readout method*, not repeat noise (`PERM_AVG.md:4-6` verdict: does not ship; its ECE 0.0869 paired value is not comparable to the 0.0475 single-order repeat, `EVALUATION_CLAIMS.md:32`).

## Gotchas (with evidence)

1. **Nominal bound ≠ guarantee.** Cal180 selected model+prompt+tau; LTT's fixed-model/i.i.d. premises fail. Quote "nominal calculation on the selection set" only. `EVALUATION_CLAIMS.md:18-32`; `Conformal.swift:6-8` states the same limit in code.
2. **Frozen test120 is report-only and already exposed.** 13 saved test120 files exist; it was not evaluated once. Never select on it. `EVALUATION_CLAIMS.md:16`; `ORCHESTRATOR_LEDGER.md` ("Do not rerun it for candidate selection").
3. **r2c's gain is partly target sharpening.** Same ids/targets as r2a; soft top 0.704→0.956 via alpha 0.1 + impute-to-8. Do not attribute to "more data". `ROUND2.md:65,74`; verified counts above.
4. **Vote frequency is not teacher probability.** Spark `q` is a 2–5-sample histogram + Laplace. Pure-KL V1 was under-confident (handled 0.21, ECE 0.178) largely because k=2 unanimous rows cap at 0.71–0.83. `ROUND2.md:21`; `build_round2.py:37-38`.
5. **Imputation inflates effective k.** 1,530/1,750 Spark-r2 rows imputed. The 0.982 statistic justifies the majority letter, not calibrated sharpness. `build_round2.py:19-20,31-32`.
6. **Trainer/eval/deployment prompts differ.** Zero-shot train vs v2+cc headline vs few-shot phone. Few-shot exemplars use canonical labels in Swift but `LABELS_V2` relabeling in the headline eval. Freeze one deployment-faithful readout for gating. `lora_r2.py:80`; `eval_round2.py:28`; `Decision.swift:218`.
7. **Warm-server ECE drift crosses gate margins.** V4 passes fresh (0.059) and fails warm (0.066) against a 0.06 clause; SHIP itself spans 0.040–0.052. Gates must pre-specify fresh+warm passes. `ROUND2.md:59-63`; `PERM_AVG.md:45-49`.
8. **ECE is readout-dependent.** Headline 0.0638 (test120 reference), 0.0475 paired single-order, 0.0869 perm-averaged are different methods/states, not repeats. Always report method + server state. `EVALUATION_CLAIMS.md:32`.

## Audit A — `label_round2.py` spending control (do not scale until fixed)

The labeler is resumable at row granularity (appends JSONL, skips done ids, `label_round2.py:57-58`) and refuses test inputs (`:32`), but its budget control is end-of-run accounting over an all-in-flight workload. Findings, smallest first:

1. **All futures submitted at once; budget checked only on completion.** `futs = [ex.submit(one, r) for r in todo]` (`:131`) creates a future for every remaining row (thousands). Each `one()` fans out to the shared `CALLS` pool (`:97`, sized `workers * k`) via `CALLS.map` for k0 then top-up votes (`:104-107`). The budget test `if prev + usd > a.budget: break` (`:145-146`) runs only as results are consumed in `as_completed` order, under the write lock. Breaking stops consumption; it does not retract HTTP requests already dispatched inside running `one()` calls. Overshoot = all in-flight items × up to k calls each. With workers=24 and adaptive top-ups, dozens of items (hundreds of calls) can be in flight past the cap.
2. **In-flight spend is acknowledged as uncounted.** The spend-log note says "in-flight calls at a hard stop are not counted (small)" (`:156`), and the earlier crashed 429 run needed a "+$0.25 conservative allowance for untracked in-flight calls" plus reconciliation from per-row usage (`spend.jsonl` rows 5–119). "Small" was true at $5 scale; at $80 scale with 6,455 rows it is the dominant error term.
3. **Token accounting counts only final successful responses.** `tin/tout` accumulate from `x.get("usage")` for non-error responses only (`:108-112`). `call()` retries up to 10 times with exponential backoff+jitter (`:77-87`); a retry after a server-processed timeout or a 429 storm bills again, but only the eventual success's usage is recorded. Failed-attempt tokens are invisible to the budget. Unparsed (`None`) votes still consumed output tokens and are counted in `votes`/`top_share` denominators, which is conservative for filtering but means paid tokens can yield a dropped row with no per-row cost record.
4. **Interrupted runs can lose the spend line entirely.** The cumulative `prev` is the sum of `spend.jsonl` (`:61`). The log line is written once at the end (`:152-156`), including for `interrupted` (`:148-149`) via KeyboardInterrupt handling — but a SIGKILL, host crash, or `os._exit` path skips it. The next resume then understates `prev` and can re-approve budget already spent. (Rows already written are still skipped by id, so labels are not double-bought; only the dollar ledger leaks.) The `os._exit(0)` at `:158` also prevents atexit/flush guarantees beyond the explicit writes.
5. **Partial-k targets masquerade as full-k.** A row stopped at k0=2 unanimous is stored with `k=2, k_max=5` and raw votes (`:118-121`), which is honest — but `build_round2.py` imputation then expands it to k_max. The labeler's cost saving (mean k 2.48 vs 5) is real; the downstream target must not pretend the saved calls were made. Additionally `top_share` uses `len(res)` (including errors) while `probs` uses valid votes only (`:115,120`); `build_round2.py:35` re-derives share over `len(lab["votes"])`. Two denominators for one concept invites silent drift if either file changes.
6. **Throttle is necessary but not sufficient.** Client throttle targets 94 RPM against the observed 100 RPM Baseten cap (`:27,64-71`) and eliminated 429s after restart (`ROUND2.md:9`). It spaces request *starts*; it does not bound concurrency, total calls, or dollars. The hard wall-clock stop (`:30,35`) similarly bounds time, not spend, and is checked per item/call, not per dispatched request.

**Smallest coherent bounded/restartable design (propose; do not implement in this role):**

- *Per-call reservation ledger (append-only JSONL, fsync per entry).* Before dispatching each teacher call, append `{item_id, call_index, reserved_usd}` where `reserved_usd` = worst-case `(max_prompt_tokens * PIN + max_tokens * POUT)` using the actual prompt token count (count locally; prompts are rendered from `prompts.chat_messages`, so input tokens are knowable) and the request's `max_tokens=768`. On response, append a settlement `{item_id, call_index, actual_usd, usage}`. Budget available = cap − sum(reservations unsettled at worst case) − sum(actuals). Unknown/billed-but-unrecorded outcomes *retain* their reservation (never auto-release on timeout; release only on a provider-confirmed non-billing signal, which generally does not exist — so treat timeouts as spent). This makes the cap hold under crashes at the cost of conservative stranded reservations, reconciled manually against the provider dashboard.
- *Bounded submission window.* Replace all-at-once submission with a window: at most `W` items in flight (e.g. W=workers) and a calls-in-flight ceiling; submit the next item only when a completion settles and the reservation check passes. Hard-stop and budget-stop then overshoot by at most one window, a known dollar bound printed at startup.
- *Durable progress.* Keep the current append+skip-done labels file (it works), but write the reservation/settlement ledger with the same append+fsync discipline as `label_local.py:44` (`flush` + `os.fsync`). On startup, rebuild `prev` from the ledger (settled actuals + outstanding worst-case reservations), not from a single end-of-run summary line. Refuse to start if the ledger's file hash/count disagrees with the labels file's done-set size beyond the in-flight window.
- *Retry accounting.* Each retry is a new reservation with its own `call_index`/`attempt`. Cap attempts per call (e.g. 4) and add a run-level retry-dollar sub-cap; 429 backoff stays, but a 429 storm now visibly consumes reservations and trips the cap instead of silently multiplying cost.
- *Partial-k honesty.* Store `k_observed`, `k_max`, and `imputed: false` at label time; let imputation (if used at all) be an explicit, separately-flagged build step whose output rows carry `imputed_to_k: N`. Default for new experiments: no imputation (see Approach A).
- *One owner per allocation.* A single labeler process owns a tranche cap recorded in `docs/training/round3_jobs.json` before launch (owner, cap, input hash, output path). No second writer appends to the same labels/spend files concurrently.

Necessary tests (extend `training/tests/test_pipeline.py`, no network): (a) reservation math — window + worst-case reservations never let committed spend exceed cap under simulated all-timeout outcomes; (b) crash-restart — kill after N settlements, restart, assert rebuilt `prev` ≥ true settled spend and done ids are not re-dispatched; (c) retry storm — stub `call` to 429 K times then succeed, assert attempts each reserved and sub-cap trips; (d) adaptive-k accounting — unanimous k0 rows reserve only k0 calls, split rows reserve top-ups before dispatch; (e) partial-k flagging — build output marks imputed rows and target denominators match the labeler's stored share definition. These are unit tests over the ledger/window logic with a stubbed transport, not a generic framework.

## Bounded larger experiment sequence

Principles (from the scaling record, tightened): one factor per step; freeze the comparison command and gate before inspecting candidate results; never tune many knobs simultaneously or move gates after seeing outcomes; keep shipping artifacts untouched; a synthetic/teacher-labeled holdout is a proxy, not deployment truth; reserve credit for evaluation and integration, and treat spending as a cost, not a success metric. Primary-source framing: compute-optimal pretraining scales model and tokens together and does not promise monotonic fine-tuning gains [Chinchilla]; Meta's post-training guidance distinguishes SFT demonstrations from RL with a cheap, objective, checkable reward [Meta post-training]. Neither licenses "more epochs ⇒ better Reflex".

### The two structurally distinct approaches

**Approach A — Extend the current vote-target data (Spark votes, more contexts).** Label some or all of the 6,455 unused pool rows with the existing Baseten Spark vote pipeline (after Audit-A fixes), build train files with *fixed* target construction, and retrain the V4 recipe. What it isolates: the effect of *context quantity/diversity* under the current noisy vote-target definition — provided alpha, imputation, filter, recipe, and readout are held fixed against a same-size control. What it cannot isolate: target quality (vote histogram vs true probabilities) or prompt effects. Cost driver: Baseten tokens. Saved round-2 actuals: 1,299 items for $3.6178 (≈ $0.0028/item at mean k 2.48, ≈586 in / 483 out tokens per item). Planning estimate at recorded rates: 6,455 rows ≈ $18 at adaptive k (allow 1.5× for retries/429/top-ups → plan $25–30); fixed k=5 roughly doubles calls (≈ $35–40). Time: RPM-capped (94/min client throttle vs 100/min observed cap); 6,455 items × ~2.5 calls ≈ 16k calls ≈ 3 h of throttled wall time minimum, plus training (~90 s/variant on H100). Risk: amplifies the known vote-target calibration defect over more contexts; nudgeNow hint-agreement was only 0.842 and notificationTriage 0.872 in `label_qc.json`, so weak-type vote noise scales too.

**Approach B — True teacher-logit distillation with the existing Glimmer (Modal vLLM).** Serve `meta-models/Muse-Glimmer-30B` bf16 via the existing `training/serve/modal_glimmer_vllm.py` (H100, logprobs ≤20) and label contexts in *one* forward pass each, storing the renormalized letter distribution exactly as `glimmer_teacher.py` does locally (but bf16 instead of IQ2_M). What it isolates: *target quality* — continuous teacher probabilities vs vote histograms — on identical contexts, and it removes vote sampling variance, imputation, and Laplace choices from the target entirely. What it cannot isolate: context quantity (pair it with a fixed context set) or teacher correctness (Glimmer QC agreement still bounds weak types; `build_train.py` confidence filtering still applies). Cost driver: Modal GPU time. At the recorded H100 $3.95/h and the repo's planning throughput guess of ~6,000 req/h (`pricing.json` glimmer-modal; an *estimate*, to be measured, not a quote), 8,245 pool rows ≈ 1.4 GPU-hours ≈ $5–6 plus boot/download fixed cost (~$2 planning figure) per labeling campaign — an order of magnitude cheaper per row than votes, with one call per row and no RPM cap. Time: dominated by vLLM boot + weight load (60 GB) on first run; thereafter ~1–2 h for the full pool at the guessed throughput. Risks: throughput guess is unverified (measure on 200 rows first); bf16-vs-IQ2_M teacher shift means B's targets are not directly comparable to the shipping 892 rows' targets — re-label a shared anchor subset with both teachers to quantify the shift; Glimmer serving is System-2 infrastructure also used by the app, so schedule labeling to avoid starving app smoke checks (scaledown window 300 s, max 1 container, `modal_glimmer_vllm.py:58-70`).

### Sequence (each step gated; no step starts on a prior step's in-flight spend)

- **Step 0 — Freeze evaluation separation (no spend).** Create new splits grouped by source-family (synthetic template family / MASSIVE / CLINC / SNIPS / generator seed) into: *train* pool, *dev* (model selection), *cal-fit* (temperature/tau/prior fitting only), and *report* (touched once per finalist). Also freeze the exact eval command: one GGUF → fresh server → pass 1 (fresh) + passes 2–3 (warm) on dev and cal-fit via `eval_round2_reps.py` semantics, plus the general-answer guardrail below. This step is the precondition for every claim in later steps.
- **Step 1 — The already-reserved pilot (Modal $5 cap, existing reservation).** V4 recipe on `r2c` (SHA `afcf82d7…d3b3`), only epochs 1→2, explicit `::main` GPU command, unique candidate name. Interpretation is narrow by design: does more optimization on identical targets help or overfit? It does not authorize promotion and does not substitute for Steps 2–3. Reject partial/aborted runs as evidence (Audit B.4).
- **Step 2 — Glimmer-logit anchor pilot (Modal, est. $3–6).** Serve Glimmer bf16, label a stratified anchor of ~600 contexts already labeled by Spark votes (spanning strong/weak types) plus ~200 fresh pool contexts. Measure: true throughput (req/h), per-row cost, letter-mass distribution, and agreement/sharpness delta between Glimmer-logit `q` and vote `q` on identical contexts. Success criterion is *measurement quality* (stable throughput, usable letter mass ≥ 0.5 rate comparable to local Glimmer), not accuracy. This prices Approach B honestly before scaling it.
- **Step 3 — Target-quality experiment (Modal training, est. $2–5).** On one fixed context set (e.g. the 892 Glimmer contexts + a fixed 1,500-row pool subset), train two candidates identical in recipe/seed/epochs differing *only* in target: (i) vote targets as in `r2a` (alpha 0.5, no imputation), (ii) Glimmer-logit targets from Step 2. Compare on dev (fresh+warm). This is the first experiment that can attribute a calibration/coverage change to target definition. Do not add imputation, label smoothing, conf-weighting, or prompt changes in the same step.
- **Step 4 — Quantity experiment, only if Step 3 says targets are adequate (Baseten and/or Modal per winner).** Hold the winning target definition fixed; scale contexts (e.g. +2,000 then +4,000 family-stratified rows) with a same-recipe control retrained on the Step-3 context count. If the winner is Glimmer logits, this step costs Modal GPU time only and Baseten stays reserved; if votes win (unexpected given round 2), spend Baseten in tranches of ~2,000 rows (~$6–12 each at adaptive k) with Audit-A reservations enforced and a stop after each tranche to re-measure. Prompt alignment (train zero-shot vs deployment few-shot rendering, with/without prior correction at train time) is a *separate* single-factor step after quantity, never bundled with it.
- **Reserve.** Hold back at least $15 Modal for finalist re-evaluation (multiple fresh/warm passes, quant identity check, drift guardrail) and integration, and at least $20 Baseten unspent until Step 4's direction is known. Total planned commitment before Step 4: pilot $5 (reserved) + Step 2 $3–6 + Step 3 $2–5 + evaluation reserve $15 ≈ $25–31 of the $110 Modal; Baseten $0 until a vote-direction win. Spending the full $110/$80 is not a goal; unspent credit after a decisive answer is a successful outcome.

*Deferred, not scheduled:* general SFT beyond the letter (e.g. training full responses or tool-call arguments) and verifiable-reward RL are separate programs (see below). No tranche above funds them. Any new model identity for those (larger student, different teacher) *needs user assignment* of provider/model/effort before dispatch and is not proposed here as an executable step.

## Promotion / regression gate (pre-register before Step 1 results are inspected)

Primary metric (single, frozen): **useful local coverage at controlled observed error on the Step-0 dev split** — specifically, handled share at the candidate's cal-fit-selected tau subject to the error constraint below, measured on the exact exported GGUF in the frozen fresh+warm protocol. Rationale: the product trades coverage against selective risk; argmax accuracy alone rewards blanket confidence, and the nominal LTT bound alone rewards tiny handled sets. Report (never select on) the nominal tightest bound, ECE, and per-type breakdowns alongside.

Promotion requires *all* of the following, on every fresh and warm pass (no averaging across passes to hide a fail):

1. *Selective-risk guardrail:* at the cal-fit tau, observed dev errors among handled = 0, or the nominal tightest bound (delta=0.1, 99-grid) is strictly below the shipping GGUF's bound measured in the *same* protocol on the same dev split, at handled share ≥ shipping share. (Cal180 continuity numbers — SHIP 10.4% @0.90 — are reported for reference; the binding comparison is same-split, same-protocol, same-GGUF-readout.)
2. *Calibration guardrail:* dev ECE (10-bin, raw confidences) ≤ 0.06 on every pass, and ≤ shipping ECE + 0.01 pass-matched (fresh-vs-fresh, warm-vs-warm). This directly addresses V4's warm-only failure; a candidate that passes only fresh does not promote.
3. *Accuracy guardrails:* dev argmax accuracy ≥ shipping − 0.01 overall, and no decision type drops more than 2/15 (dev per-type n) vs shipping without a recorded, accepted reason. Weak types (nudgeNow, notificationTriage) are reported individually, not hidden in the mean.
4. *General-answer guardrail:* `DRIFT_CHECK` protocol on the candidate GGUF — checkable answers must not drop below shipping (23/23) and routing/JSON collapse must remain 0; mean per-token KL vs base reported. A System-1 win bought by general degradation does not promote.
5. *Abstention proxy:* CLINC OOS stress false-confident rate at the shipped tau must not exceed shipping (0.25% at 0.90) by more than the run-to-run replicate delta observed for shipping itself. Labeled a proxy, not an error rate.
6. *Identity/reproducibility:* exact GGUF SHA-256, llama.cpp build, server flags (`-c 4096 -t 4`), and pass indices recorded; at least 2 fresh + 2 warm passes per finalist; test120, if run at all for a single winner, is report-only, once, after the promotion decision is recorded, and cannot reverse it.

Regression rule: any guardrail failure = reject (keep ep1 shipping), record the failing pass, and do not adjust thresholds, bins, or pass selection post hoc. Moving a gate after seeing outcomes converts the next result into another selection-set calculation. If no candidate promotes, the correct deliverable is the negative result plus the Step-2/3 attribution of *why* (targets vs quantity vs prompt), which is what the remaining credit should buy next — not a relaxed gate.

## System 1 improvement vs general SFT vs verifiable RL (do not conflate)

- *System 1 classification (this program).* The Reflex letter *is* the behavior; the reward for a correct letter is only verifiable against gold/teacher labels, so "decision accuracy" measures teacher/gold agreement on hand-authored and synthetic distributions. Improving it (Steps 1–4) does not demonstrate better reasoning, argument extraction, or task completion (`EVALUATION_CLAIMS.md:36`). Claims must say "decision-label accuracy/coverage on [split]", never "the assistant got smarter".
- *General SFT.* Teaching the 1B to produce full answers, tool-call JSON, or multi-step plans requires demonstration responses (not letters), a different loss surface, generation-based evaluation, and drift measurement. The current letter-only LoRA neither does this nor evidences it; `sft_unsloth.py` with hard letters is still classification SFT. A general-SFT proposal needs its own data licensing, throughput estimate, and task-success metrics, and *needs user assignment* for any new teacher/student identity.
- *Verifiable RL.* Per Meta's post-training guidance, RL fits when success is cheap and objective to check (a file exists, a number matches, a test passes) and should start from an SFT checkpoint that already behaves [Meta post-training]. Candidate verifiable rewards here would be things like "the chosen tool call's deterministic preconditions hold in a simulator" — *not* "a teacher liked the letter". A teacher's confident opinion is not a verified phone action (scaling record requirement 7). No RL step is funded above; the honest precursor is Step 3's target-quality answer plus a simulator-backed reward definition, neither of which exists yet.

## Data adequacy: what can start now vs what claims need

*Existing data adequate to start experiments:* the 8,245-row pool + 1,790 Spark labels + 892 Glimmer labels suffice for Steps 1–3 (duration, anchor, target-quality) because those steps compare recipes/targets on fixed contexts; their internal validity does not need new independent data, only family-clean dev/cal-fit carve-outs from existing rows (Step 0). The 6,455 unused pool rows are adequate *contexts* for a quantity step; their labels (votes or logits) are what costs money.

*Independent data needed to make claims:* any statement about real iPhone traffic, deployment error rates, or a post-selection guarantee needs (a) a defined target population and sampling plan, (b) newly collected labels untouched by model selection, split by source-family into dev / cal-fit / report as in Step 0, and (c) a fixed pipeline before the report split is seen (`EVALUATION_CLAIMS.md:41-43`). A synthetic or teacher-labeled holdout remains a proxy for that claim no matter how large it grows, because its contexts and labels share the generators/teachers being evaluated. Budget implication: reserve labeling credit for a *human-anchored* report set (even a few hundred independently authored/verified items outweigh thousands more synthetic rows for claim-making), and do not spend the full Baseten tranche on synthetic votes before that set exists. Frozen test120 cannot fill this role — it is small, exposed, and report-only.
